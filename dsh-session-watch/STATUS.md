## 3. 本轮修掉的十六个真实缺陷（全部由实机运行或对照实验暴露）

### 缺陷一：审批闸门从未生效

`AWAITING_TYPES` 原本写着 `approval/request`、`user/question`、`plan/proposal` ——
枚举本机 **178 个真实日志的全部事件类型**后确认，**这三个名字一个都不存在**。
真实事件名是 **`approval/asked`**（10 个会话出现过）。

后果：停在审批上的会话被判成 `stalled`，而 `stalled` 是唯一可自动恢复的判定 ——
**开自动恢复就会往一个等你批准工具的会话里发「继续」，等于替你按了确认。**

修复：改用真实事件名，并新增「**未被回答的 `ask_user_question`/`exit_plan_mode` 调用**」这一识别
（这类等待没有事件类型，证据是缺失的 `tool/result`；本机实测该工具被调用 40 次）。

### 缺陷二：每一次恢复其实都在抛错

开启自动恢复后账本立刻记下：

```
Cannot read properties of undefined (reading 'throwIfAborted')
```

`sessionController.prompt` 有**两层**，签名不同：内层 `async prompt(request)`（文档描述的是这个），
外层 `prompt(request, signal) { signal.throwIfAborted(); ... }`（插件实际调用的是这个）。
原实现只传了 `request` —— **此前每一次自动恢复都在真正开始前就失败了**。

修复：始终传 `AbortSignal`，并给它 30 秒超时（一个专门发现停摆的插件，自己绝不能在恢复时挂住）。

### 缺陷三：新代码在旧进程里会让**整个专家半**挂载失败

**发现的经过**：在推演「不重启会怎样」时，我注意到专家半 `import` 了 Host 半**新加的**导出，
于是做了个对照实验：用一个**缺少新导出**的 `plugin.js` 去加载专家半。

```
SyntaxError: The requested module './plugin.js' does not provide an export named 'readLedger'
```

**根因**：loader 按插件名缓存模块。进程里还是旧 `plugin.js` 时，新专家半的**静态 import 直接抛错**——
而**缺失导出是加载期错误**，所以整个专家半（三个工具，包括两个纯只读的）**全部挂载失败**，
报错信息里还完全看不出「需要重启」这回事。

**修复**：把账本抽成独立模块 `lib/ledger.js`，两半各自引用它，**专家半不再静态依赖 Host 半**。
唯一真正需要 Host 半的函数（`resumeSession`）改成**惰性 import**，所以即使它不可用，
也只影响那一个写工具并能明确报错，而不是把只读工具一起拖死。

**已写成三条防回归断言**（`proxy-apply.test.mjs`）：专家半不得静态 import Host 半、
Host 半仍须 re-export 账本 API、两半必须读**同一个**账本。

> 这个缺陷**不会**影响本次交付（重启后两半同代，本来就能加载），
> 但它会让「重启后专家半万一没挂载」变成一个极难诊断的现象，所以顺手根除。

### 缺陷四：两半执行的**不是同一套策略**

**发现的经过**：在核对「不重启会怎样」时，我把专家半的挂载记录和 Host 的实际配置对了一下，
发现两边记的 `stallMs` 不一样 —— Host 是 900000（来自 patch），专家半是 **300000**（它自己的默认值）。

**根因**：两半的设置来自**不同地方**：

| | 设置来源 |
|---|---|
| Host 半 | `~/.dsh/cordis.patch.yml` 的 `config:`（`stallMs: 900000`，`resume: {...}`） |
| 专家半 | preset 里的那一行 —— **完全没有 `config`**，于是 `apply(ctx, undefined)` 退回自己的硬编码默认值 |

后果有两条，第二条是**主动误导**：

1. 专家认为"5 分钟没动静就是停摆"，Host 认为 15 分钟 —— **专家对自己的判定口径和面板不一致**；
2. **即使用户已经把 Host 的自动恢复打开，专家仍然会以 `disabled` 为由拒绝每一次恢复** ——
   因为它根本看不到那个开关。于是面板说"已启用"、专家说"未启用"，
   而 `disabled` 这个理由对专家自己那份过期副本来说是真的，**对部署来说却是假的**。

**修复**：专家半的策略**以 Host 快照为准**（Host 本来就是策略的唯一真源，正如它已经是判定的真源），
每次调用时现读，所以用户改配置（热更新）后专家立刻跟随。行自己的 `config` 仍然生效，
只是被快照里的值覆盖 —— 想给某个 preset 不同设置的写法依然可行。

**已写成 10 条断言**（`config-divergence.test.mjs`），包括"完全没有快照时仍拒绝而非按宽松默认放行"，
以及"Host 不可达时 `session_roster` 必须**降级报告**而不是抛错"——
抛错会让专家拿到一个无法推理的不透明失败，而它是专家**第一个**调用的工具。
另外两条锁住**第 2 层与第 3 层的联动**：`session_roster` 必须把**每个会话的恢复决定**
（`willResume` / `reason` / `detail`）交给专家，否则专家无法解释"为什么这个没被恢复"，
只能对着判定猜策略；并且必须区分**"停摆了"**与**"真的会被恢复"**——
这两件事不同，把前者说成后者等于承诺一个不会发生的动作。

### 缺陷五：面板**丢掉了**新加的字段

**发现的经过**：我给 Host 快照加了 `expert`（专家是否挂载）并写进 `/watch` 与面板，
但面板测试一直显示"未挂载"——而我在测试里明明填的是 `mounted: true`。

**根因**：Client 半的 store 用**白名单逐字段**采纳 Host 的响应：

```js
function adopt(body) {
  patch({
    stalled: ..., attention: ..., totals: ..., stallMs: ...,
    resumeEnabled: ..., resumePolicy: ..., resumed: ...,
    // ← `expert` 不在这张表里，所以被静默丢弃
  })
}
```

白名单本身是刻意的（"明确组件理解哪些字段"），但它的失效方式很坏：**新字段被无声吞掉**，
面板于是永远显示"未挂载"，而原因看起来完全像是 Host 那边的问题。

**修复**：`expert` 整块传递并做最小归一化，注释写明为什么不再逐字段抄。

> 缺陷四和五都是"两半之间对不齐"，而且**都不会让测试变红**——它们只会让面板说假话。
> 这也是为什么我给这两处都补了断言，而不是只在代码里写注释。

### 缺陷六：面板每次轮询都在做全量扫描

`/state` 每次请求要 3.5 秒 —— 而侧边栏正是靠它刷新的。
缓存只在**并发**时生效，任何不重叠的读取都会重扫全部 190 个会话；
后台定时器的产出没有任何人消费。详见 §5.4（含修复前后的实测对比）。

> 这条与前五条不同：它**不产生错误答案**，只产生糟糕的体验。
> 但它同样属于"单测全绿、实机难受"那一类——测试从不断言延迟，
> 所以只有真的去**量**才会发现。这也是我给路由补上计时断言的原因。

### 缺陷七：快照报告的是**意图**，不是**结果**

`collectSessions` 先算出"这个会话将被恢复"，`buildSnapshot` 再据此动作。
但返回的那一行**保留着动作前的值**，于是：

- `resume.willResume` 在恢复**已经发出**之后仍是 `true`；
- `resume.attempts` 比账本少 1（增量发生在行建好之后）；
- `resume.lastAttemptBy` 在**执行了那次尝试的同一轮扫描里**是 `null`。

实测时 `/watch` 出现了自相矛盾的输出——先打印
「已发送续跑提示」，紧接着对**同一个会话**打印「本轮将恢复…（尚未自动恢复）」。

这不是措辞问题。第 2 层的全部设计前提是**每个自动动作都可报告**
（"用户看不见的动作，和 harness 自作主张没有区别"）；
一个报告**计划**而不是**结果**的面板，根本无法用来判断那条续跑到底发出去了没有。

**修复**：动作落地后**重写该行**，让它描述结果（`reason: resumed` / `resume-failed`、
真实次数、作者署名、已完成的时间戳），并**清掉已经过时的 `handoff`**。

### 缺陷八：Host 尚未就绪时**白烧一次尝试机会**

watcher 的第一次扫描在进程启动后**约 1 秒**就跑。那时 `sessionController`
可能还在初始化（它等 `workspaceRegistry`，而后者要从磁盘读会话语料），
于是这次恢复返回 `no-controller`。

旧代码把它当作普通失败记下——后果是：

- 一个**恰好在启动时停摆**的会话，会因为一条**根本没发出去**的续跑而损失两次机会中的一次；
- 重启两次之后，面板会显示「已达上限」——**声称插件试过两次并放弃了，而它其实一次都没发**。

`no-controller` 说的是**这个进程**的状态，不是会话的状态。所以现在它被**报告**、
稍后**重试**，但**不计入**尝试次数（`reason: host-not-ready`）。

> 这条缺陷是我搭隔离宿主时**偶然撞见**的：先看到账本里一条 `no-controller`，
> 一度以为是自己 fixture 摆错（确实也摆错了，见 §5.5），
> 但**时间戳对不上**——扫描发生在启动后 1 秒，而 controller 几秒后才就绪。
> 两个问题同时存在，得分开修。

### 缺陷九：手动 `/resume` 路由不记账

它刻意豁免自动闸门（那是你的判断，不是策略的判断），但**豁免闸门不等于可以隐身行动**。
账本是"到底对哪个会话试过什么"的唯一记录，跳过它会让面板的历史是错的。
已改为记录并署名 `by: manual`，并沿用同一条守卫——没能抵达 Host 的调用不消耗额度。

### 缺陷十：专家看不到策略已经给出的"下一步"

Host 在策略停手时算出了 `handoff`，但 `session_roster` **没有把它传给专家**。
专家**就是**那个下一步，拿不到它就只能自己重新推导同一个结论——
更糟的是，它无法区分"一个会话已经等了你几个小时"和"刚刚停下来的"。
现在 `nextStep` 与作者署名（`lastAttemptBy`）都会传过去。

### 本轮还补了三处"以后才不会踩"的覆盖

- **新页面 + 旧 Host**（刷新页面但还没重启就会出现）：旧 Host 不发
  `expert` / `handoff` / `lastAttemptBy`，面板必须退回诚实的"未挂载"，而不是崩掉或打印 `undefined`。
- **客户端自带轮询**：我一度以为面板只在点击时更新（那样徽标会漏报），
  查证后确认它每 20 秒轮询、窗口聚焦时也刷新、并在清理时取消定时器——三条都写成了断言。
- **测试里的开合状态必须"读"而不是"猜"**：写这组用例时我两次因为假设面板是开着/关着而误判。
  现在 `openPanel()` / `closePanel()` 从渲染结果**读取**状态，不会与组件漂移。

### 缺陷十一：面板声称"已自动恢复 N 次"，而那 N 次可能一次都不是自动的

**这是重启后复核真实账本时发现的，而且是被我自己的验证脚本触发的。**

`verify-live.mjs` 为了拿"调用级 signal 证据"会 `POST /resume` —— **那是写操作**，
会真的往会话里发一条"继续"。它挑的是 `candidates[0]`，所以在你的宿主上跑它，
就往你**两个真实会话**里注入了续跑提示；又因为每次尝试都记账，
还**花掉了它们的自动恢复额度**。

会话被 nudge 过是**不可撤销**的。一个"验证"脚本绝不该做这件事，更不该替你选会话。

**两条修复**：

1. `verify-live.mjs` 改为**默认只读**。要拿调用级证据必须**显式指定**一个可牺牲的会话
   （`--resume-probe <sessionId>`）。已验证：跑完后账本尝试数**不变**（3 → 3）。
2. 记账之后暴露的第二个问题：额度是**共享**的（谁花的都算），这本身是**对的**——
   上限的作用是限制"一个会话总共被打扰几次"，放宽它会让手动 nudge 过两次的会话
   再多收两条自动消息。**错的是说法**：`decideResume` 汇报「已自动恢复 2 次（上限 2）」，
   而那两个 `by` 都是 `"manual"`。**那是对用户的虚假陈述。**

现在按历史如实区分（四种情形都有断言）：

| 账本历史 | 修复前 | 修复后 |
|---|---|---|
| auto ×2 | 已自动恢复 2 次 | 已自动恢复 2 次（正确，不变） |
| manual ×2 | **已自动恢复 2 次** ❌ | 已被手动/专家续跑 2 次（自动 0 次） |
| auto + manual | **已自动恢复 2 次** ❌ | 共尝试 2 次（自动 1、手动/专家 1） |
| 无历史 | 已自动恢复 2 次 | 已尝试 2 次（不编造归因） |

允许恢复时的文案同样修了：手动之后不再说"第 2 次自动恢复"，而是
「此前已有 1 次续跑（其中自动 0 次），本次为自动发起」。
**共享额度这条安全属性没有放松**——手动尝试仍然计入上限。

> 这条顺带解释了为什么"验证脚本"必须区分读写：
> 我为了证明一个 bug 修好了，制造了另一个 bug。

### 缺陷十二：催促文案硬编码"自动续跑"——手动/专家发的也这么自称

**发现方式很特别：我收到了自己插件的 nudge。**

续跑工作完成后，我的会话收到一条消息：

> （**自动**续跑）上一轮在你的步骤执行中途停止了，日志里没有 turn/end。
> 停止位置：turn=9 step=5，最后事件 tool/call。

我第一反应是"harness 是不是自作主张了？"——而这**正是本项目要消灭的那种不确定性**。
查账本后确认坐标 `turn=9 step=5` 对应我早先探针发出的一次 `by=manual`：
它是**手动**的，只是**文案在撒谎**。

**为什么这条重要**：这句话是**写进会话正文的**，会永久留在用户的对话记录里。
手动或专家发起的续跑却自称"自动"，等于在用户自己的日志里留一句假话——
与缺陷十一（"已自动恢复 N 次"）同一类。

**修复**：`buildNudgeText` 增加 `origin`，三条路径各自署名：

| 发起方 | 写进会话的首行 |
|---|---|
| 自动路径 | （自动续跑）… |
| 手动路由 | （手动续跑 — 你本人发起）… |
| 专家工具 | （用户代理专家发起）… |
| 未知来源 | （续跑 — cron）… （**绝不冒充自动**） |

**顺带发现并修掉同一个错**：面板和 `/watch` 用二选一渲染作者
（`auto ? '自动' : '专家'`），所以**手动 nudge 被显示成"专家"**。
三处现在都能区分：自动 / 你本人 / 专家。

> 教训：**文案也是行为的一部分。** 我修好了"记账要区分作者"，
> 却没检查"写给用户看、写给会话看的字"是否也区分了作者——
> 同一个概念的四处表述，我只改了两处。

### 缺陷十三：催促文案断言"上一轮停止了"——但它送达时可能早已过期

**又是自己的插件教会我的，而且这次有两个样本。**

修完缺陷十二后，我的会话**又**收到一条 nudge，坐标 `turn=9 step=15`。查账本：
两次尝试都停在 21:05，**没有新触发**——这是队列里的旧消息。

但关键事实是：

| | |
|---|---|
| nudge 创建 | 21:02:57（`turn=9 step=5`）、21:05:01（`turn=9 step=15`） |
| 我收到时 | 21:38 |
| 会话当时已在 | **`turn=11`** —— 比它声称的位置**晚两轮** |

消息说「上一轮在你的步骤执行中途**停止了**」，而收件方早已越过那里两轮。
**那是一句假话**，而且收件 agent **无从判断**——消息里只有 `turn`/`step`，
没有时间戳，也没有"若你已越过则忽略我"。

**两次我都得自己推断出它已过期**，其中一次还差点去重做早已完成的工作。

**修复**：文案改为**陈述观测**而非断言事实，并明确给出逃生出口：

```
（自动续跑）检测到 turn=9 step=15 处没有 turn/end，日志最后事件 tool/call。
这条消息可能在你越过该处之后才送达。若你已经继续过，它就已经过期——请忽略它，
不要重做任何已完成的工作，也不要因为它而重新解释计划。
若确实停在那里，请从该中断处继续未完成的工作。
```

改动要点：

- 「上一轮**停止了**」→「**检测到**…处没有 turn/end」（观测，而非事实断言）；
- 明说**可能迟到**、**允许忽略**、给出**判据**（"若你已经继续过"）；
- 核心指令保留但加了前提（"若**确实**停在那里"）。

> 这是同类问题的**第三次**出现：**系统对用户（或对自己）说了一句它无法保证为真的话。**
> 前两次是"已自动恢复 N 次"和"自动续跑"，这次是"你停在这里"。
> 共同点是：**陈述了一个在写下时就可能已经过期的状态。**

### 缺陷十四：自动恢复的时间戳从未写进账本（`now` 是 `undefined`）

**这是第一次真实自动恢复时暴露的——而且是它自己暴露的。**

你在生产环境触发首次自动恢复后，账本显示：

```
session-A  attempts=2
  by=manual  at=2026-10-06 21:01:33   ok=True
  by=auto    at=1970-01-01 08:00:00   ok=True   ← 时间戳是 epoch 0
```

**根因**：`collectSessions` 把时间戳命名为 `generatedAt`，
而 `buildSnapshot` 解构的是 `{ now, sessions }`：

```js
const { now, sessions } = snapshot   // now === undefined
...
const entry = { ..., at: now, ... }  // 每条自动记录都带上 undefined
```

`JSON.stringify` 把 `undefined` 变成 `null`，于是**每一条自动尝试的审计时间戳都是空的**。
手动路径走 `Date.now()`，不受影响——**这就是它一直没被发现的原因**。

**严重性分级（诚实说明）**：**退避和上限完全正常**。
`recordAttempt` 里 `lastAttemptAt = Number.isFinite(entry?.at) ? entry.at : Date.now()`，
`undefined` 会回落到正确的当前时间。**机制是对的，只有审计轨迹在撒谎。**

而这恰恰最值得修：账本存在的意义就是**归因**——
一份时间戳读不出来的历史，回答不了"监视器上次是什么时候碰它的？"

**修复**：显式取 `snapshot.generatedAt` 并加回落，不再依赖下游的偶然兜底。

**反证**：我把修复临时改回 `undefined`，测试变红；恢复后变绿——
证明这条断言真的能抓住它，而不是恰好通过。

### 缺陷十五：重启后**所有**会话瞬间被判停摆 —— 两次真实误报

**这是你报告"停摆的会话恢复了"之后查出来的，属于本项目最严重的一类问题：误报。**

我重放了 nudge 发生那一刻的判定。**同一份日志、同一时刻**：

| `running` | 判定 | 静默 |
|---|---|---|
| `false` | **stalled** | **0s** |
| `true` | **idle** | 0s |

`stallMs` 是 **900 秒**。两次 nudge 发生在进程启动后 **13 秒**，静默分别是 **6s** 和 **0s**。
**前提根本不成立。**

**根因是一句被代码推翻的注释。** `plugin.js` 里写着：

```js
// A missing registry degrades to "nothing is running", which can only cause a
// REPORT, never a wrong automatic action.
```

**这句话是假的。** `!running` → `stalled`，而 `stalled` 是**唯一**可自动恢复的判定。

而 `running` 的含义是"**本进程**里有没有这个会话的 agent"——两种完全不同的情况被混为一谈：

1. 驱动器死了、留下未闭合的轮次 —— 该报；
2. **本进程里没有它的 agent** —— 重启后**每个**会话都是这样。

加上 `!running` 分支**完全没有时间闸门**（而 `running` 分支有），
于是启动瞬间凡"上一轮没结束"的会话全被判停摆。

**修复**：静默窗口**对两种状态一视同仁**。死掉的驱动器仍会被抓——它停止写入，
静默会增长到超过窗口。窗口只是把检测**推迟到"静默"真正有意义的时候**，不会漏掉。

**边界实测**：899s → `idle`，900s → `STALLED`，1 小时 → `STALLED`。

**顺带修掉的测试缺陷**：`resume-wiring.mjs` 的"停摆"fixture **没有 `time` 字段**，
所以 `silentMs` 恒为 0——它算作停摆**正是因为那个 bug**。
fixture 与实现共享同一个错误假设，于是测试证明了自洽而不是正确。已改成真实时间戳。

### 缺陷十六：193/193 个会话都在给"下一步"建议

修完缺陷十五后顺手量了 `handoff` 的分布，结果是**每个会话都有**：

```
subagent 113/113   idle 67/67   empty 8/8   aborted-by-user 5/5
```

内容是「规则判定不该自动恢复（**idle**）。…可以先手动续跑」。

**两个错**：

1. **建议本身是错的** —— 对 113 个 subagent 和 67 个正常 idle 会话说"你可以手动续跑它"，
   而它们**从未停摆**。告诉用户去续跑一个没停的东西，是错误建议。
2. **音量淹没了重点** —— 每个会话都带建议时，真正需要关注的那一行就找不出来了。

**根因**：`handoffFor` 把 `not-stalled` 当成**一个**状态，但它其实是"除上限外的全部拒绝"，
涵盖 `idle` / `subagent` / `empty` / `aborted-by-user` / `awaiting-approval`——
其中**只有一个**需要人。

**修复**：建议只出现在**会话真的卡在用户身上**时（`awaiting-approval`），或额度用满时。
停在审批上的会话**不再被宣传成"可续跑"**——那等于邀请用户替它回答一个尚未回答的问题。

实测：**193 → 0**。同时新增 `handoff-parked.test.mjs`，
用真实 fixture 确认"停在审批上"这一支**真的被走到**
（原先那条断言在实时宿主上显示 "(0 checked)"，即**空过**——
一个从不执行自己分支的测试证明不了任何事）。

### ★★ 首次真实自动恢复：完整的端到端证据

上面那个时间戳缺陷，正是**首次真实自动恢复**顺带暴露的。这件事本身值得单独记录，
因为此前我只能说"机制在隔离宿主里验证过，生产环境仍是待命"。

**账本**：

**两个会话都真的前进了**：

| `a75aa1e4` | turn=**2** step=10 | turn=**3** step=6 | ✅ +1 轮 |

**最关键的一步**：账本说"controller 接受了"，但那只是 API 层的事实。
所以我去读**会话自己的日志**，确认消息真的进了对话正文

- `seq 2217`（21:01，旧代码）：断言「上一轮…**停止了**」
- `seq 2830`（23:02，新代码）：陈述「**检测到**…」并**承认可能过期**

证据存于 `test/artifacts/first-auto-resume-proof.txt`。

> 这同时回答了另一个此前悬着的问题：**nudge 确实会进对话**，
> 不只是写进账本。这一点之前只有间接证据。

### 这十六个缺陷的共同教训

**fixture 必须来自观测到的真实数据，而不是代码期望的形状。**
前两个缺陷都是「实现和测试共享同一个错误假设」——
`detect.test.mjs` 和 `resume-wiring.mjs` 的 fixture 也用了不存在的 `approval/request`，
stub 也照内层签名写成 `prompt(request)`，于是**测试全绿而功能全坏**。

现在两个套件的 stub 都**模拟真实的双层形状**并断言 signal 存在，
缺 signal 或事件名写错都**不可能再通过**；第三个缺陷由模块边界的三条断言锁住。

### 5.0b ★ 作用域隔离：专家看得见，普通会话看不见（实测，非推断）

"注册了"和"agent 真的能调用"是两件事。所以 `expertScope` 报告通过 registry 的
作用域租约**实际读取**两个作用域的工具表：

此前这条只靠结构断言（`standard` 的 patch 里没有那一行），现在是测量。
（证据存于 `test/artifacts/scope-isolation-proof.json`。）

前面所有闸门证据都来自 fixture。这一条不是——它是在**你的宿主、你真实的会话、
自动恢复已经开着**的情况下测的，而且**时机是偶然撞上的**：

                  读一下它在等什么，或 ... 手动续跑。

  ✓ 1 个等待审批的会话全部被正确拒绝，且给出了下一步提示。

**为什么这条最有说服力**：这是**唯一会让风险变成现实**的配置组合——
自动恢复开着 + 一个真实会话正停在审批上。而它自然发生了，
不是我在隔离环境里摆出来的。

> 这反而**第二次证明**了它为什么必须改成 opt-in：
> 它连"等待审批的会话"都会去碰，而那是闸门刻意保护的。
>
> 随时可复查：`node test/verify-approval-gate-live.mjs`（只读）
> 证据存于 `test/artifacts/live-approval-gate.txt`。

### 5.1 ★ signal 修复的 A/B 实机对照

同一个脚本 `test/verify-signal-live.mjs` 分别打两个宿主，得到**决定性对照**：

| 宿主 | 代码代次 | `/resume` 的返回 |
|---|---|---|
| 隔离宿主 :19510 | **修复后** | `code: "session/not-found"` —— **带类型的 controller 错误** ✅ |
| 你的宿主 :19387 | **修复前** | `code: null` + `Cannot read properties of undefined (reading 'throwIfAborted')` ❌ |

**判据是返回的"形状"，不是成功与否**：旧代码在**进入 controller 之前**就抛原始 TypeError
（没有 `code` 字段）；修复后的代码能走到 controller 内部，于是拿到一个带 `code` 的 `RemoteError`。
`session/not-found` **是通过**——它证明调用真的抵达了 `resolveAgent`，
而那只可能在 signal 存在且未中止时发生。

这条对照把"我改了代码"和"改动真的生效"分开了，也是此前 `resume-wiring.mjs`
用 stub 无法证明的部分（stub 说的是**我以为的**契约，这里是**真实**契约）。

### 5.2 ★ 审批闸门缺陷的**反证**（把"我修好了一个安全漏洞"变成可检验的命题）

说"修复前会误恢复等待中的会话"是个**主张**，不是证据。所以
`test/approval-gate-counterfactual.mjs` 重建了**修复前**的 `AWAITING_TYPES`
（那三个照着上游类型名写、本机从不发出的名字），再用**当前**判定逻辑跑同一批 fixture：

```
PASS  COUNTERFACTUAL: 旧闸门让停在 approval/asked 的会话漏成 stalled
PASS  COUNTERFACTUAL: 旧闸门让停在未回答 ask_user_question 的会话漏成 stalled
PASS  THE FIX: 现行闸门正确识别出 awaiting-approval
PASS  and `stalled` is the ONLY auto-resumable verdict
```

最后一条是把"分类错误"升级成"安全漏洞"的那一环：如果 `stalled` 只是被**报告**得不同，
这个缺陷就只是措辞问题；正因为它是**唯一会被自动恢复**的判定，
分类错误才等于"替你按了确认"。

### 5.3 ★ 第 2→3 层的交接：策略停手后必须给出下一步

**发现的问题**：目标要求"停摆会话先经专家诊断，再由策略决定如何续跑"。
第 1、2 层是自动的，第 3 层是判断。可当策略**刻意停手**时
（`attempts-exhausted`，或规则判定不该碰的 `not-stalled`），面板当时只说"转为仅报告"——
**没有任何下一步**。

那等于把用户重新丢回项目要解决的那个原点：手里有一个停下来的会话，不知道该干什么。
**循环没有闭合。**

**修复**：给策略停手的会话附一个 `handoff`，指明具体动作，并且**只在专家真的挂载时才提它**
（指向一个没装上的工具，比什么都不说更糟）：

```
session-real-stall    reason=attempts-exhausted
  -> [attempts-exhausted] 已用满自动恢复次数。建议用用户代理专家读它的
     输入输出找根因（session_review），或 GET .../resume?sessionId=... 手动续跑。

session-approval-park  reason=not-stalled
  -> [needs-human] 规则判定不该自动恢复（awaiting-approval）。用用户代理专家
     读一下它在等什么，或 GET .../resume?sessionId=... 手动续跑。
```

注意两条分支的区别：**前者**把专家当作下一步（自动化放弃了，该由人/专家接手）；
**后者**只说"去读它在等什么"——因为那是规则**刻意**不碰的等待，
若在提示里叫你去"强制续跑"，就等于教你替用户按确认。

**已在隔离的真实宿主上实测**（`maxAttempts: 0` 让停摆会话立刻进入耗尽分支），
面板与 `/watch` 都会显示"下一步"。6 条断言，其中包括"禁用策略**不**产生交接"
——那是用户自己的配置，不是策略放弃了，对每个会话都催一遍纯属噪声。

### 5.4 ★ 面板每次轮询都在做全量扫描（性能缺陷）

**发现的经过**：给 `/state` 计时，发现**每次请求都是 3.5 秒**——
而侧边栏正是靠这个路由刷新的。也就是说面板每次轮询都要等 3.5 秒。

**根因**：`refresh()` 的注释写着"折叠重叠调用、让扫描不阻塞请求"，
但它**只在有并发调用时返回缓存**：

```js
if (refreshing && cached !== null) return cached   // 只在"正在扫描中"才复用
refreshing = true
cached = await buildSnapshot(...)                  // 否则一律重扫
```

于是**任何不重叠的读取都会触发一次全量扫描**（190 个会话 ≈ 3.5s）。
后台定时器确实在按 `pollMs` 扫描，但**它产出的结果没有任何人消费**——
缓存只用来合并同一瞬间的请求，从不用于"这份数据还够新"。

**修复**：加一个 2 秒的新鲜度窗口——窗口内的读取直接返回内存里的快照。
正常轮询路径因此变成 O(1)，磁盘工作回到定时器上，而不是压在用户的请求上。
`/refresh` 与 `/resume` **绕过**窗口：前者是用户明确要当前数据，
后者的判定是整个动作的依据，两者都必须看到实时状态。

**实测**（同一台真实宿主，190 个会话）：

| | 修复前 | 修复后 |
|---|---|---|
| 首次 `/state` | 3571ms | 2957ms（真扫） |
| 再次 `/state` | 3529ms | **0ms**（同一份快照） |
| 第三次 `/state` | 3551ms | **1ms** |

**已加 2 条回归断言**（`plugin-smoke.mjs`），判据是**结果**而不是内部实现：
重复读取必须返回同一份 `generatedAt`，且耗时降到首次的四分之一以下。

### 5.5 ⚠ fixture 摆错会伪装成插件 bug（三次真实教训）

搭隔离宿主时我连续踩了三次 **fixture 格式**的坑，**每次的现象都看起来像插件的缺陷**：

| 错误 | 后端真正的报错 | 表面现象 |
|---|---|---|
| 日志直接放 `sessions/<id>/`，缺编码的 project 目录 | `workspaceRegistry` 初始化失败 | `session-controller` 变 `pending`；插件看到**没有** controller，每次恢复都 `no-controller` |
| 文件名用 `session.v4.jsonl`（本部署配置的是 `zstd`） | `uses .jsonl, but this backend is configured for compression "zstd"` | 同上 |
| 整个文档压成**一个** zstd 帧 | `first frame is not exactly one header line` | 读会话时报 "corrupt session log" |

**正确写法**（`_recon/write-gate-fixtures.mjs`）：

```
<home>/sessions/<编码后的project>/<sessionId>/session.v4.jsonl.zstd
```

- project 目录要编码，**连续的分隔符折叠成一个 `-`**：
  `C:\probe` → `--C-probe--`，`C:\agent\dsh\plugin` → `--C-agent-dsh-plugin--`；
  其余非字母数字字符按码点转义成 `~<hex>`；
- 文件名必须带 `zstd`；
- 内容是**逐行独立的 zstd 帧**（真实日志一个 11 事件的会话有 155 个帧——按写入批次成帧）。

**为什么这条值得记**：这三种错误在**插件侧的表现完全一致**——账本记下
`no-controller` 或 `gateway/internal`，而真正的原因在**宿主的启动日志**里
（`workspaceRegistry` 那一行），插件的日志一个字都不会提。
**一个摆错的 fixture，会让人去修一个不存在的 bug。**

> §5.0b 的作用域隔离与 §5.2 的审批闸门验证**不受影响**：那两次用的是
> **从真实 home 复制来的日志**（格式天然正确），所以 `sessionController` 当时在场。

## 7. 怎么用第 3 层（专家）

**新开一个会话**，在创建时选择 **「User Proxy」** preset。

> preset 在会话开第一个轮次前锁定，之后不能改；已存在的会话保留它创建时的修订。
> 所以必须**开新会话**。

届时可用的三个工具：

| 工具 | 作用 | 读写 |
|---|---|---|
| `session_roster` | 全机会话清单 + 判定 + 为什么不会被恢复 | 只读 |
| `session_review` | 深读某会话的输入输出 + 停止归因 | 只读 |
| `session_resume` | 续跑某会话（唯一写动作，闸门与自动路径共用账本） | 写 |

persona 里已经写明**怎么用**这三个工具（先读证据再下结论、把拒绝当决定报告、
不得把读不到说成"一切正常"），那四条要求都有断言锁住（见 §5 的 `preset-drift.mjs`）。

## 8. 已知边界（诚实列出）

- **重启这一步只能由你或 `/restart` 完成**：插件无法从宿主进程内部重启应用。
- **专家半的挂载原本只能等重启，现在已经实测证明。**
  我用 `Win32_Process.Create`（WMI）在**隔离的 `DSH_HOME`** 里另起了一个真实宿主，
  它自己写下的挂载记录显示 `proxyMounted: true`、三个工具全部注册、五个服务全部在场（§5.0）。
  在你**正在用的**宿主上仍需重启加载同一份代码——但"这份代码挂不上"这个风险已经排除。
  已确认的还有：组合树里两行都在（`--dump-config` 对账），
  且**两半解析到同一模块实例**（`shared-instance.test.mjs`）。
- **`profiles\node_modules\@deepseek-ai\*` 是 223 个断链 junction**（指向已删除的旧安装）。
  宿主实际代码只在 `app.asar` 内。排查时**不要**依 profile 目录。
- **专家有真实权限扩张**：能读全机所有会话正文。只挂给 `user-proxy`，不挂给 `standard`，
  `preset-drift.mjs` 有断言锁住这一点。
- **`.agent-presets/` 目录格式已废弃**：本机现存的 `router-standard` 是旧安装（0.1.2-rc.1）的遗留物，
  当前版本不读取它。
